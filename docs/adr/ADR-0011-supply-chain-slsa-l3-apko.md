# ADR-0011 — Tobby's own supply chain: SLSA Build L3, melange+apko, reproducible builds

## Status

Accepted — 2026-07-11

## Context

Tobby verifies signatures, scans for vulnerabilities, and gates what enters
hardened zones. Its own releases will be scrutinized by the most demanding
reviewers its users employ — and they should be. A supply-chain gate whose own
supply chain is opaque has no standing. Tobby's build pipeline is therefore a
product feature, not an internal concern, and it must be in place **from the
first commit** (milestone 0.1), not retrofitted.

Reference frameworks in scope for the target environments: **SLSA**, OWASP SCVS,
NIST SSDF. One point needs stating explicitly to prevent a recurring
misunderstanding: **SLSA v1.0 defines Build levels L0–L3 only.** The "L4" that
older documents cite existed solely in the retired v0.1 draft (hermetic,
two-person-reviewed builds) and is not part of the current specification. Tobby
therefore targets, and claims, **Build L3 — the highest defined level — plus
reproducibility on top** (informally "L3+"). Any document claiming "SLSA L4" is
citing a dead spec.

Deliverables per release: static binaries for Linux and Windows, container
images, SBOMs, signatures, and provenance — all consumable and verifiable in
disconnected environments.

## Decision

### Provenance: SLSA Build L3 via slsa-github-generator

Releases are built on GitHub Actions using the **`slsa-github-generator`
reusable workflows** (`generator_generic_slsa3` for binaries, the container
workflow for images). The reusable workflow is the accepted pattern for Build L3
on GitHub: the provenance is generated by a **trusted builder isolated from the
project's own workflow code**, so a compromised repository workflow cannot forge
its own attestations. Provenance is signed via Sigstore and published with each
release.

Consumer verification is **documented, not just possible** — the release notes
of every version include the exact commands:

```bash
# verify a release binary against its SLSA provenance
slsa-verifier verify-artifact tobby-linux-amd64 \
  --provenance-path tobby-linux-amd64.intoto.jsonl \
  --source-uri github.com/tobby-fetch/tobby \
  --source-tag v1.0.0
```

### Reproducible Go builds

All binaries are built with:

- `CGO_ENABLED=0` — pure-Go static binaries, no host libc contamination;
- `-trimpath` — no build-machine paths in the binary;
- fully pinned toolchain and dependencies — exact Go version in `go.mod`,
  modules locked by `go.sum`, GitHub Actions pinned by commit SHA;
- `SOURCE_DATE_EPOCH` set from the commit timestamp for any embedded or packaged
  timestamps.

Goal: an independent rebuild from the same tag yields **bit-identical binaries**,
letting an air-gapped consumer who cannot call Sigstore infrastructure verify a
release by rebuilding it. Reproducibility is asserted in CI by a double-build
comparison job.

### Container images: melange + apko, targeting zero CVE

Images are **not** built from Dockerfiles:

1. **melange** packages the Tobby binary as a signed **apk** package with its own
   build-time SBOM;
2. **apko** assembles the final image declaratively on a **Wolfi** base:
   explicit package list, no shell or package manager in the runtime image, a
   **native SBOM generated at build time** (not reconstructed by a scanner
   afterwards), reproducible output by design.

```yaml
# apko.yaml (excerpt) — the image is a declaration, not a script
contents:
  repositories:
    - https://packages.wolfi.dev/os      # mirrored internally for release builds
  packages:
    - tobby            # our melange-built, signed apk
    - ca-certificates-bundle
accounts:
  run-as: 65532        # non-root
entrypoint:
  command: /usr/bin/tobby
```

The image target is **0 known CVEs at release time**, which Wolfi's rebuild
cadence makes realistic rather than aspirational.

### SBOM, scanning, and freshness

- A **CycloneDX SBOM** is generated for every binary and image, **signed with
  cosign**, and attached to the release and the image (referrers/attached
  artifact).
- **Trivy runs in CI** on every build — the scanner Tobby embeds gates Tobby
  itself (dogfooding with ADR-0008); a release cannot ship violating the same
  default policy Tobby applies to user artifacts.
- **Renovate** keeps Go modules, GitHub Actions, and base packages current via
  automated PRs.
- **Weekly automated rebuilds** of the latest release image pick up Wolfi package
  fixes even when Tobby's own code has not changed, so the "current" image does
  not silently accumulate CVEs between releases.

## Consequences

### Positive

- Tobby's release page is its best sales document for security-conscious
  adopters: L3 provenance, signed CycloneDX SBOMs, zero-CVE images, and a
  documented independent-rebuild path.
- Reproducibility gives air-gapped consumers a verification path that requires
  no online infrastructure at all — the strongest guarantee available to them.
- The declarative melange/apko pipeline eliminates whole bug classes of
  Dockerfile builds (undeclared contents, scanner-guessed SBOMs, mutable base
  tags).
- One signature ecosystem (Sigstore) across Tobby's releases and the artifacts
  Tobby verifies at runtime (ADR-0007) — operators learn one model.

### Negative

- Hard coupling of the L3 claim to GitHub Actions and the slsa-github-generator
  trusted builder. Accepted for v1: it is where the project is hosted and where
  the strongest ready-made L3 story exists. A future migration would need an
  equivalent isolated-builder story.
- melange/apko is a less universal skill set than Dockerfiles; contributor
  documentation must cover the release pipeline. Mitigated by the pipeline being
  small, declarative, and CI-owned.
- Reproducibility is a treadmill: toolchain updates can perturb it, so the
  double-build CI job must be a release gate, not an FYI.
- Windows deliverables get reproducible signed binaries and provenance, but no
  apk/apko equivalent; their supply-chain story is binaries + SBOM + provenance
  only. Documented openly.

### Neutral

- Wolfi package repositories are an online dependency **of the release build
  only**; consumers of Tobby need no connectivity. Release builds mirror the
  required packages, consistent with the pinning policy.

## Alternatives considered

### Dockerfile multi-stage build onto distroless

The proof-of-concept's approach and the industry default. Rejected for the
product because: image contents are the *outcome of a script* rather than a
declaration, making drift and undeclared files possible; there is no native
build-time SBOM (scanners must reconstruct contents afterwards, less accurately);
reproducibility of Docker builds is fragile (layer timestamps, base-tag
mutability); and `distroless` offers no package-level rebuild cadence comparable
to Wolfi for holding a 0-CVE line between releases.

### ko

Excellent minimal-friction Go image builder, and it does produce SBOMs. Rejected
because it controls only the final image assembly: no signed intermediate package
(melange's apk), less control over the base filesystem contents, and no path to
the apk-repository distribution channel that melange gives us for free. For a
project whose image *is* a security claim, the extra control of melange+apko is
worth the extra configuration.

### GoReleaser alone

GoReleaser automates multi-platform builds, archives, and even cosign signing,
and can emit provenance. Rejected **as the provenance mechanism** because Build
L3 requires provenance generated by a builder **isolated from the release
workflow the maintainers control** — the property the slsa-github-generator
reusable workflow provides and a self-driven GoReleaser run does not. GoReleaser
may still be used for release ergonomics (changelogs, archive layout) underneath
the trusted builder; it just cannot carry the L3 claim by itself.
